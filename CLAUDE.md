# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Next.js dev server on `http://localhost:3000`.
- `npm run build` — production build. Use this after structural changes to verify the app still compiles. The build requires `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to be set (placeholders are fine when smoke-testing).
- `npm run start` — serve the production build locally.

There are no tests configured.

## Environment

Copy `.env.example` → `.env.local` and fill in the two Supabase values. The example file's header comment is the canonical setup checklist (project creation → API keys → running the SQL migrations). Apply every file in `supabase/migrations/` in numeric order in the Supabase SQL Editor — `0001_init.sql`, `0002_tutor_profile.sql`, `0003_tutor_dashboard.sql`, `0004_browse.sql`, `0005_default_public.sql`, `0006_profile_images.sql`, `0007_email_confirmed.sql`, `0008_service_area_geo.sql`, `0009_subject_catalog.sql`, `0010_rename_certificates_to_exams.sql`, `0011_year_levels_and_general.sql`, `0012_remove_headline.sql`, `0013_slug_regen_and_race_safe.sql`, `0014_tutor_subjects_order.sql`, `0015_delete_own_account.sql`, `0016_oauth_default_role.sql`, `0017_full_name_not_blank.sql`, `0018_onboarded.sql`, `0019_year_min_default_k.sql`, `0020_ai_usage.sql`, `0021_verification_and_notifications.sql`. Without Supabase set up, the public pages (`/`, `/browse`, `/tutor/[slug]`) render empty states because they query real data at request time; signup/login also fail.

Auth emails (signup confirmation) are sent **by Supabase** over **Resend custom SMTP**, configured entirely in the Supabase dashboard (Project Settings → Authentication → SMTP Settings) — there is **no Resend key in `.env.local`**, because the app never sends mail itself. This replaces Supabase's built-in sender (capped ~2 emails/hour, poor deliverability). `supabase/email-templates/confirm-signup.html` is the source-of-truth for the confirmation template (pasted into Authentication → Emails → Confirm signup). Without a verified Resend domain the sender is `onboarding@resend.dev`, which only delivers to your own Resend account email; verify a domain (SPF/DKIM/DMARC) to send to anyone. See the README "Configure auth email (Resend SMTP)" section. **Exception (slice 21):** the tutor-verification flow is the one place the *app itself* sends mail — `lib/email/send.js` calls the Resend **HTTP API** directly (`RESEND_API_KEY`, `EMAIL_FROM`; unset = no-op + console log) for the admin approve-link email and the tutor's notification emails.

## Architecture

### Big picture
- **Next.js 14 App Router + JavaScript (no TypeScript) + Tailwind CSS.** Pages live under `app/`. The public pages (`/`, `/browse`, `/tutor/[slug]`) are **server components** that fetch from Supabase at request time; small client subcomponents (search hero, hover cards, filter sidebar, rate card, save button) handle the interactive bits and are imported by the server page. Auth pages (`/signup`, `/login`) and the dashboard are client components because they're built around forms / live editing.
- **All public reads come from Supabase.** `lib/data.js` (the old hardcoded `TUTORS` array) was deleted in slice 4. Helpers in `lib/supabase/tutors.js` are the only path to tutor data.
- **Design system is inline.** The original prototype was an HTML/CSS/JS handoff (preserved in `_design/`, gitignored). Styling is intentionally a mix of Tailwind utility classes for layout and inline `style={{ ... }}` for the specific colors / radii / borders that came from the design. Don't refactor inline styles to a global stylesheet without reason — they keep the design tokens local to where they're used.

### Supabase

- **Schema** lives in `supabase/migrations/`, applied in numeric order:
  - `0001_init.sql` — Option B layout: a shared `profiles` table 1:1 with `auth.users`, plus role-specific extension tables `tutor_profiles` and `student_profiles` keyed by the same uuid. A `handle_new_user()` trigger reads `role` and `full_name` from `auth.users.raw_user_meta_data` and creates the matching `profiles` + role-specific row atomically on signup. Self-only RLS.
  - `0002_tutor_profile.sql` — expands `tutor_profiles` with the columns the public profile page needs (bio, atar, rate, availability JSONB, rating, …), adds a seeded `subjects` reference table (17 HSC/UCAT/LSAT subjects), a `tutor_subjects` join table, and ordered child tables `tutor_packages` / `tutor_experience` / `tutor_education` (each with a `position` column). Adds public-read RLS on tutor data; tutor self-write on their own rows.
  - `0003_tutor_dashboard.sql` — renames `atar_rank` → `rank`; adds dashboard-editor columns (`headline` (removed in `0012`), `rank_subject`, `verified`, `delivers_in_person`, `delivers_online`, `service_area` jsonb, `verifications` jsonb, `visibility` text with check constraint); converts `credentials` from `text[]` to `jsonb` of `{label, icon}`. `service_area` JSONB shape is `{ suburb, radiusKm, lat?, lng?, geocodedSuburb? }` — `lat`/`lng` are populated by the geocoder, `geocodedSuburb` is the suburb string those coords came from so the editor knows when to re-geocode. The DB column itself stays untyped JSONB; the shape is enforced in JS.
  - `0004_browse.sql` — adds `tutor_profiles.slug` (unique) plus a `generate_unique_slug(name)` helper; extends `handle_new_user()` to populate the slug on new tutor signups and backfills existing rows; changes the `visibility` default from `'public'` to `'unlisted'` (later reverted in `0005`); adds filter indexes on `visibility`, `city`, `atar`, `rate`; adds a second SELECT policy on `profiles` allowing public read for rows where `role = 'tutor'` (so the browse join can return tutor names).
  - `0005_default_public.sql` — reverses step 5 of `0004`: sets the `tutor_profiles.visibility` default back to `'public'`, so new tutor signups are listed on `/browse` as soon as `handle_new_user()` creates the row. Existing rows are left untouched (optional commented backfill for leftover `'unlisted'` rows).
  - `0007_email_confirmed.sql` — gates public listing on email confirmation. Adds `tutor_profiles.email_confirmed_at`, a mirror of `auth.users.email_confirmed_at` (the anon read role can't see the `auth` schema). `handle_new_user()` copies it on insert (non-null when the project auto-confirms); a second trigger `on_auth_user_email_confirmed` (AFTER UPDATE OF `email_confirmed_at` on `auth.users`) propagates the timestamp when the user later clicks the confirmation link, flipping them visible. The public query helpers in `lib/supabase/tutors.js` filter `email_confirmed_at IS NOT NULL` alongside `visibility = 'public'`, so an unconfirmed signup never appears on `/`, `/browse`, or `/tutor/[slug]`.
  - `0008_service_area_geo.sql` — makes the tutor's service-area radius drive location search. Lifts `service_lat` / `service_lng` / `service_radius_km` out of the `service_area` JSONB into real columns (backfilled from the JSONB; `saveTutorProfile` writes both going forward) so SQL can filter by distance. Adds `tutors_within_service_radius(lat, lng, include_online)` — a plain-SQL haversine function (no PostGIS/earthdistance extension) returning ids of public + confirmed tutors whose travel radius covers the point, OR-ing in online-delivery tutors. `getTutorsForBrowse` calls it as its "resolve ids first" step.
  - `0009_subject_catalog.sql` — replaces the 17 seeded subjects with an extensive **certificate-scoped** Australian catalog (254 subjects across 8 senior-secondary certificates — HSC, VCE, IB, QCE, SACE, WACE, TCE, ACT — plus a `TEST` group for admissions/aptitude tests like UCAT, GAMSAT, LAT). Adds a `certificates` reference table (`code` PK, `name`, `jurisdiction`, `external_exams`, `position`; public-read RLS) and a `subjects.certificate_code` FK; **drops the `subjects.name` UNIQUE constraint** (the same display name recurs across certificates) while `slug` stays the unique canonical key, now **certificate-prefixed** (e.g. `vce-biology`, `hsc-biology`; tests are bare, e.g. `ucat`). Wipe-and-reseed: existing `subjects` + their `tutor_subjects` links are cleared. Subjects are now identified by **slug, not name**, throughout the data layer (`getSubjects` returns exam-aware rows; the editor stores/saves slugs; `saveTutorProfile` resolves slugs → ids). Display sites label subjects via `subjectLabel()` in `lib/subjects.js` (`"VCE Biology"`, or just `"UCAT"` for the TEST group).
  - `0010_rename_certificates_to_exams.sql` — pure rename of the 0009 concept: table `certificates` → `exams`, column `subjects.certificate_code` → `subjects.exam_code`, and the RLS policy. No data changes. The codebase uses **"exam"** terminology throughout from here on (`getSubjects` rows carry `exam`/`examName`; `groupByExam` + `subjectLabel` in `lib/subjects.js`; the `exam:exams(...)` embed in `getSubjects`). HSC/VCE/etc. and the `TEST` group are all "exams".
  - `0011_year_levels_and_general.sql` — two K–12 additions. (a) `tutor_profiles.year_min` / `year_max` (int, default 7 / 12, check `0–12` + `min ≤ max`) — the year-level range a tutor teaches; backfilled to 7–12, drives the `/browse` year filter and the profile card. `saveTutorProfile` writes both; `getTutorsForBrowse` matches a tutor when their range covers any selected year. (b) A new `GENERAL` exam group (position 0) seeding English/Mathematics/Science/History/Geography (slugs `general-*`) for pre-Year-11 tutoring — flows through the exam-code-driven catalog automatically; labelled bare (no prefix) like `TEST` via `lib/subjects.js`. Year labels/formatters live in `lib/yearLevels.js`.
  - `0012_remove_headline.sql` — drops `tutor_profiles.headline`. It overlapped with the tagline (`bio`), so the **tagline now owns that role**: it's the single one-line subtitle shown under the tutor's name on both the public profile and the browse card, and the column `q` (overall) search matches. Existing headline text is backfilled into `bio` first, but only where `bio` is empty. `tutor.role` (the editor's old headline key) is gone; the unrelated auth `role` and `tutor_experience.role` are untouched.
  - `0013_slug_regen_and_race_safe.sql` — fixes two slug issues. (a) **Race-safety**: the old `generate_unique_slug()` → insert path could let two concurrent same-name signups compute the same suffix and fail one on the unique constraint. A new race-safe core `_assign_tutor_slug(id, name)` UPDATEs the slug in a retry loop that catches `unique_violation` and bumps the suffix (random-suffix fallback after 50 tries). `handle_new_user()` now inserts the tutor row with a placeholder slug (the uuid) and then calls the core — still mirroring `email_confirmed_at` as in 0007. (b) **Regenerate on rename**: `assign_tutor_slug(name)` is an authenticated RPC (scopes to `auth.uid()`, so a caller only ever changes their own slug) that `saveTutorProfile` calls whenever the display name changes, so the name-derived `/tutor/<slug>` URL no longer goes stale. `_assign_tutor_slug` has execute revoked from the API roles; the old `generate_unique_slug()` is left defined (now unused) so nothing referencing it breaks.
  - `0014_tutor_subjects_order.sql` — gives `tutor_subjects` a `position` column (was an unordered join table) so a tutor can set the order their subjects appear in. The settings editor's `SubjectPicker` (multi/box variant) renders the selected chips as a native HTML5 drag-and-drop list — reordering rewrites the `tutor.subjects` slug array, which `saveTutorProfile` persists as `position` (sequential over the kept slugs). Every read returns subjects in that order (`.order("position", { foreignTable: "tutor_subjects" })` added to `getTutorProfile`, `getTutorBySlug`, and the two `BROWSE_SELECT` queries), so the browse card and public profile match the editor. **Existing tutors default to alphabetical**: the migration backfills existing links alphabetically by display label (exam-prefixed like the editor; `TEST`/`GENERAL` bare). New picks in the editor append to the end of the array; the tutor drags to set their own order.
  - `0015_delete_own_account.sql` — adds `delete_own_account()`, a `SECURITY DEFINER` RPC scoped to `auth.uid()` (modelled on `assign_tutor_slug` in `0013`) that deletes the caller's own `auth.users` row. That cascades through `profiles` → `tutor_profiles`/`student_profiles` and their child rows, wiping the account. Execute is granted to `authenticated` only. Powers the **Delete account** card on `/account`. Known gap: `profile-images` Storage objects aren't FK-linked, so they're left orphaned (acceptable for v1).
  - `0016_oauth_default_role.sql` — makes `handle_new_user()` OAuth-safe. Google signups never hit `/api/auth/signup`, so their `raw_user_meta_data` carries no `role` and no `full_name` (only Google's `name` claim). Re-defines the trigger (same race-safe slug + `email_confirmed_at` mirror body as `0013`) with two `coalesce` defaults: `v_role` falls back to `'tutor'` (required because `profiles.role` is `NOT NULL`), and `v_name` falls back to the `name` claim. So a first-time Google user lands as a confirmed tutor with a real name-derived slug.
  - `0017_full_name_not_blank.sql` — DB backstop for the required display name. Normalizes any existing blank `profiles.full_name` to `NULL`, then adds the `profiles_full_name_not_blank` CHECK (`full_name IS NULL OR btrim(full_name) <> ''`). NULL stays allowed so OAuth signups with no name claim aren't blocked. The UI (`IdentitySection`/`SaveBar` in `app/settings/sections.js`) and `saveTutorProfile` (trims → throws on blank) enforce the same rule earlier.
  - `0018_onboarded.sql` — adds `tutor_profiles.onboarded` (boolean, NOT NULL, default `false`) to drive the first-login `/onboarding` questionnaire. The default means every new `handle_new_user()` insert is un-onboarded automatically (no trigger change); existing rows are backfilled to `true` so current tutors skip the wizard. Surfaced by `getTutorProfileForEditor` (`onboarded`) and flipped by `markOnboarded()` in `lib/supabase/tutors.js`; `app/settings/page.js` redirects `onboarded === false` users to `/onboarding`.
  - `0019_year_min_default_k.sql` — lowers the `tutor_profiles.year_min` column default from `7` to `0` (Kindergarten) so new signups default to **K–12** instead of Years 7–12 (`year_max` already defaults to `12`). Only affects new inserts (no backfill); the `0011` CHECK already permits `0`. The JS fallbacks match (`defaultTutor` in `SettingsEditor`, `getTutorProfileForEditor`'s `year_min ?? 0`). The `YearLevelsSection` slider renders a K–12 tick scale beneath the dual-handle range.
  - `0020_ai_usage.sql` — backs the AI tagline/bio generator's abuse limit. Adds `ai_usage` (PK `(user_id, day)`, `count`) with self-only SELECT RLS and no write policy, plus two `SECURITY DEFINER` RPCs scoped to `auth.uid()` (modelled on `delete_own_account` in `0015`): `consume_ai_credit()` — the atomic gate, a single conditional `UPDATE ... WHERE count < limit` that increments today's UTC-day count only while under the **hardcoded** daily limit (10; not a parameter, so a client calling the RPC directly can't raise its own cap) and returns `(allowed, used, day_limit)`; and `refund_ai_credit()` — decrements (floored at 0), called by the route only when Groq itself fails so a provider outage doesn't burn the credit.
  - `0021_verification_and_notifications.sql` — backs the **tutor verification request flow**. (a) Adds `tutor_profiles.verification_status` (`none`/`pending`/`verified`/`rejected`, default `none`, CHECK) + `verification_requested_at`; the existing `verified` boolean (`0003`) stays the display flag, set true **only on approval**. (b) Adds a `notifications` table (`user_id` FK→`auth.users`, `type`, `title`, `body`, `read`, `created_at`) with self-only **SELECT + UPDATE** RLS (mark-as-read) and **no INSERT policy** — rows are written by the service-role client from the API routes. (c) Adds `request_tutor_verification()` — a `SECURITY DEFINER` RPC scoped to `auth.uid()` (modelled on `assign_tutor_slug`, `0013`) that flips `none`/`rejected` → `pending` (idempotent). Approval has **no RPC** — it runs through the service-role client in `/api/verification/approve` because the admin has no session when clicking the email link. The verified ranking boost lives in `lib/ranking.js` (`VERIFIED_BOOST`, added in `rankingScore`). **Verified** is shown in the `/settings` completion checklist via `RANKING_CONFIG.uncountedCriteria` (ticks once approved) but is **excluded from the percentage** — verification is admin-gated, so a tutor can still reach 100% on their own. Dev shortcut: `supabase/utilities/verify_user.sql` flips one tutor verified by id.
- **Verification / email / service-role (slice 21)**: a tutor requests verification from the `/settings` sidebar (`components/RequestVerification.jsx`) or the final `/onboarding` step. `lib/supabase/admin.js` is a **server-only service-role client** (bypasses RLS) used to write notifications, read user emails (`auth.admin.getUserById`), and approve. `lib/notifications.js` `notifyUser()` is the single path that inserts a notification **and** emails the user (so "every notification is emailed" holds). `lib/email/send.js` sends via the Resend **HTTP API** (`RESEND_API_KEY`/`EMAIL_FROM`; unset = no-op + console log) and holds the templates. `lib/verifyToken.js` signs/verifies the HMAC approve-link token (`VERIFICATION_APPROVE_SECRET`). `saveTutorProfile` deliberately **does not** write `verified`/`verification_status` (server-controlled — a tutor must not self-verify).
- **Signup flow**: the form (`app/(auth)/signup/page.js`) does **not** call `supabase.auth.signUp` directly — it POSTs to `/api/auth/signup` (`app/api/auth/signup/route.js`), the authoritative server-side gate. That route re-validates the password against `lib/password.js`, the email format against `lib/email.js`, and confirms the domain can receive mail (DNS MX → A/AAAA fallback) before calling `supabase.auth.signUp({ email, password, options: { data: { full_name, role } } })` server-side. The role chip sets `role` in user metadata; the database trigger — not the client — decides which extension table gets a row. Do not insert into `profiles` or extension tables directly from the client; let the trigger handle it. The route returns `{ status }`: `"session"` (confirmation disabled → cookies written on the response, client redirects to `/settings`), `"confirm"` (check-your-email), or `"exists"` (empty `identities` → point to login). Student signup is disabled in the UI; only Tutor accounts can be created.
- **Clients**: `lib/supabase/client.js` for client components (`createBrowserClient`), `lib/supabase/server.js` for server components / route handlers (`createServerClient` wired to `cookies()`). `middleware.js` calls `supabase.auth.getUser()` on every request to refresh the session cookie — the pattern is from the official `@supabase/ssr` docs and the matcher excludes static assets.
- **Query helpers** (`lib/supabase/tutors.js`) — all take a supabase client as first arg so they work from both server and browser contexts:
  - `getTutorsForBrowse(supabase, params)` — paginated `/browse` query. `params` is `{ q, name, subjectSlugs[], lat, lng, atarMin, rateMax, yearLevels[], modes, sort, page, pageSize }`. Filters by `visibility = 'public'`. Two distinct text searches: `q` is the **overall** search (matches the tagline `bio`/`city`/`suburb` on `tutor_profiles` OR the tutor's `full_name`), `name` filters on `full_name` only. Because `full_name` lives on the joined `profiles` table (un-filterable inside a top-level PostgREST `.or`), name matches resolve to tutor ids first — `name` intersects into `filteredIds`, while `q`'s name hits are folded into the `.or` as an `id.in.(...)` term. Both subject (`subjectSlugs`) and location (`lat`/`lng`) likewise resolve to a set of tutor ids first — subjects via a `tutor_subjects` lookup, location via the `tutors_within_service_radius` RPC — then the (intersected) ids are applied with one `.in("id", ...)` so the exact count + pagination stay correct. **Location means in-person proximity**: `modes` is a multi-select (`online` / `inperson`). The geo filter is skipped entirely when *only* online is selected (online serves everywhere); otherwise it runs with `p_include_online` true only when both modes are selected (so online tutors are OR-ed in), and false for in-person-only / no-mode (so a purely-online tutor doesn't show up under every suburb). Returns `{ tutors, total }` with each tutor mapped through the internal `tutorRowToCard`.
  - `getFeaturedTutors(supabase, limit, excludeId)` — top-N by `rating desc nulls last, review_count desc`. Used by `/` and the "Similar tutors" sidebar.
  - `getTutorBySlug(supabase, slug)` — full detail-page shape via internal `tutorRowToDetail`, including normalised `availability` (handles both the `{hours, days, grid}` shape and the bare 2D array the settings editor currently writes). Returns null if no public tutor matches.
  - `getSubjects(supabase)` — the exam-scoped subject catalog (flat, sorted by exam then subject position; each row `{ name, slug, exam, examName }`). Feeds the `SubjectPicker` on the filter sidebar, hero search, and settings editor; group it with `groupByExam` from `lib/subjects.js`. (The old `getSubjectNames` was removed when the editor moved to slug identity, and `getDistinctCities` went away when the city `<select>` became a geocoded suburb autocomplete.)
  - `getTutorProfile(supabase, id)`, `getTutorProfileForEditor(supabase, id)`, `saveTutorProfile(supabase, id, tutor)` — used by `/settings`. The editor helper returns camelCase keys matching the editor's in-memory state; `saveTutorProfile` does scalar update + replace-all on the four child tables (subjects, packages, experience, education), not transactional.

### State & navigation
- **Filter state on `/browse` lives in the URL.** `BrowseFilters.jsx` calls `router.replace()` with a new query string on every change, and the server page re-runs the Supabase query. Repeated `subject` params encode multi-select subjects; repeated `year` params (integers, K=0 … Year 12=12) encode multi-select year levels. Every filter change drops `?page=` so pagination resets. The "Year level" filter matches a tutor when their `[year_min, year_max]` range covers any selected year (see `getTutorsForBrowse`); year labels/formatters live in `lib/yearLevels.js`.
- `components/TopNav.js` is auth-aware: when a session is active, the right-hand side collapses Browse + Settings + Log out into a single dropdown anchored to the user's avatar chip; when logged out, only Log in + Sign Up render (no Browse link). The navbar is `z-40` to sit above the settings editor's own `z-30` sticky save bar.
- Navigation between pages uses `next/link` (`Link`) for static cases and `useRouter().push(...)` for form-submit redirects.

### Components
- `components/ui.js` exports the design primitives: `Avatar`, `VerifiedTick`, `OnlineDot`, `Chip`, `Button`. These are the building blocks used across all pages — prefer extending them over inline styles when adding new UI.
- `components/Icon.js` is a single-file Lucide-style SVG set (40+ icons). Add new icons here rather than importing an icon library; the file is intentionally self-contained.
- `components/TutorCard.js` is the canonical hover-animated card. The lift is now driven by `motion/react` variants (`cardVariants` with `rest` / `hover` states) rather than `useState(hover)` — `whileHover="hover"` plays `y: -4` + a small `rotate` wobble settling on 0 plus a shadow/border ease, and `animate="rest"` interpolates everything back symmetrically on leave. Other lift-on-hover cards in the codebase (e.g. `components/HomeHowItWorks.jsx`) follow the same shape. Cards link to `/tutor/${tutor.slug}`. The footer credentials and the subject row beneath it use `CredentialChipsRow` / `SubjectChipsRow` — both render the chips off-screen first, measure them with a `ResizeObserver`, then show as many as fit on one line plus a `+N` / `+N more` pill. The `recalc` closure null-guards both refs internally (not just at effect start) because the `ResizeObserver` callback can fire after the container unmounts (parent re-render, conditional rendering swap, Fast Refresh) — otherwise `containerRef.current.offsetWidth` throws.
- Home-page client subcomponents (`components/HomeHero.jsx`, `HomeHowItWorks.jsx`, `HomeCta.jsx`) exist so the home page itself can stay a server component while still hosting interactive widgets (search dropdowns, hover lifts, navigation buttons). `HomeHero` builds a `/browse` query string from its picks (`subject` slug, `lat`/`lng`/`place`, `year`) and `router.push`es it.
- `components/SubjectPicker.jsx` is the shared exam-first subject picker fed by `getSubjects()` (grouped with `groupByExam`). `mode="single"` (hero search, sidebar single-select) or multi-select (settings editor); it emits subject **slugs**, matching the `?subject=` URL contract on `/browse`.
- `components/ServiceMapLeaflet.jsx` is a `"use client"` Leaflet map (OSM tiles by default, CARTO Voyager swapped in after >3 `tileerror` events). It imports `leaflet/dist/leaflet.css` and touches `window` at module init, so callers **must** dynamic-import it with `{ ssr: false }`. The settings editor (`app/settings/sections.js`) imports it directly via `next/dynamic`; the server tutor page imports it through the thin `app/tutor/[slug]/ServiceAreaMap.jsx` client wrapper.

### Maps and geocoding
- Service area is rendered as a real Leaflet + OpenStreetMap map (no API key, no account). Geocoding uses **Nominatim** as the primary provider, falling back to **Photon** (Komoot, also OSM-based) on failure / rate-limit. Both are public, free, no key.
- `lib/geocode.js` exposes `geocodeSuburb(suburb)` (server-only, single result). `lib/places.js` exposes `searchSuburbs(q)` (server-only, list of matches for typeahead — Photon primary since it's built for autocomplete, Nominatim fallback). Nominatim's public usage policy requires an identifying `User-Agent` header — keep that intact in both files if you refactor. Both cache in-process by lowercased query.
- `app/api/geocode/route.js` and `app/api/places/route.js` are thin proxies so the client never calls Nominatim/Photon directly (avoids CORS/UA-policy issues).
- `components/SuburbAutocomplete.jsx` is the shared client picker (debounced fetch to `/api/places`, `variant="bar"` for the home search bar / `variant="box"` for sidebar + settings). Selecting a suggestion already carries `{lat, lng, state}`, so the home page and browse get coords without a second round-trip, and `ServiceAreaSection` writes them straight into `tutor.serviceArea` (`geocodedSuburb` is set so the debounced `/api/geocode` effect — kept as a fallback for legacy rows loaded without coords — doesn't re-fire). On Save, `SettingsEditor.onSave` retries the geocode only if the picked suburb is somehow missing coords.
- `ServiceAreaCard` on `/tutor/[slug]` renders the Leaflet map **only when** `serviceArea.lat` and `serviceArea.lng` are present; otherwise it hides the map block entirely and shows just the "In-person within N km of <suburb>" text line. There is no SVG placeholder on the public page.
